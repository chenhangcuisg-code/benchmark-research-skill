# Benchmark research

Use the user's catalog and requested taxonomy as the scope. Give every listed benchmark or protocol variant a stable ID and its own detailed entry; shared underlying data does not make variants interchangeable. Preserve the user's distinctions between chapters, metrics, datasets, protocols, and proposals. Do not silently drop unresolved entries.

Before collecting, read [the evidence rules](references/evidence.md). Prefer the official release, paper supplement, author repository, and pinned dataset files. Use mirrors or derivative datasets only after checking record identity and explaining exactly which official version or split they do and do not establish. Record the access attempt and error for gated or missing originals. A project page, abstract, synthetic illustration, configuration row, or nearby benchmark is not an original test case.

For each entry, explain the task, inputs and outputs, model requirements, evaluation protocol and metric, official category fields, covered and uncovered categories, real cases, gold-answer visibility, source version/split/record locator, dependencies, redistribution rights, and remaining gaps. Keep original case content separate from your explanation. If no original is public or the item is a protocol/metric, state that plainly. “A case was found” never means “the full dataset or all categories were collected,” and source auditing never implies that a model evaluation was run.

For self-authored verifiable cases, keep the complete solver-visible prompt and inputs separate from the private oracle, reference answer, and hidden checks during difficulty pilots. Test the oracle with correct and near-miss submissions, then run an independent strong solver on only the blind package and record its time, tools, and exact result. A deterministic answer key proves verifiability, not frontier difficulty; do not label a case `hard` or frontier-validated when the blind pilot solves it quickly. Explain the distinct research capability each new case tests instead of copying a reference repository's question pattern.

When the user requires complete data before delivery, use the [complete-collection gate](references/evidence.md#complete-collection-gate). Keep an explicit blocking ledger and continue checking official files, paper supplements, author repositories, and identity-checked mirrors until every requested item meets the agreed completeness scope. A paper excerpt, prompt template, or related benchmark cannot fill an original-row gap. Do not release a final handbook with unresolved `partial`, `restricted`, or `unavailable` entries as if the task were complete.

For a large catalog or an explicit dashboard request, use a searchable, navigable dashboard as the main reading artifact. Read [the dashboard format](references/dashboard-format.md) for the normalized record contract, reusable builder, offline packaging, and browser checks. Use the existing Markdown and audit records when converting a PDF deliverable; extract PDF text only when no structured source exists. Preserve every entry ID and original audit state. Separate a concise overview, complete explanation, original cases, and source files; connect them with stable routes and backlinks. Long JSON should offer field reading and unchanged raw content. Use the five overview fields (`Benchmark | 具体数据例子 | 数据分类 | 题目类型 | 模型需要做到`) across cards, comparisons, and exports without squeezing the entire catalog into one table.

When the user requests PDFs, use [the PDF delivery format](references/delivery-format.md); PDF is also a useful optional source view from a dashboard. Make one compact PDF per requested chapter and keep one audit section per benchmark. Do not generate thousands of PDF pages merely to satisfy an inherited format when the user has chosen a dashboard. Preserve original case values, necessary context, and limitations in the local research record. For a public PDF or dashboard, publish case text, gold values, and media only when the rights of those specific materials permit it; otherwise provide source/version/row locators, field names, hashes, and an access note without implying the public file contains the original. Store permitted long inputs and multimodal attachments in addressable files with record locators and SHA-256; link a per-entry full-record index when long evidence is kept outside the compact PDF. A reference to a local file or a dataset/code license does not grant rights over third-party questions, gold values, figures, or art.

Maintain machine-readable inventory, entry audit, and public-file manifest as described in [the record contract](references/record-contract.md). For a PDF handbook, run `scripts/audit_delivery.py --root <output-dir> --check-pdf` and inspect representative rendered pages from every chapter. For a dashboard, run `scripts/audit_dashboard.py --root <dashboard-dir>`, then exercise actual browser interactions under `file://`, narrow and desktop layouts, and static HTTP when relevant. Verify search scopes and late-loading records, internal routes and backlinks, long records, downloads, and ZIP contents. Record the checks actually performed and correct failures. These scripts check structure and file integrity, not facts, rights, or visual quality.

Report entry/chapter counts, case-section counts without equating them with unique dataset records, status distribution, search coverage, still-missing originals, and the dashboard/ZIP/PDF paths actually produced. Link the manifest and review log. Publish to an external repository only when that action is in the user's authorized scope. The research report's case data and this skill's source code have separate redistribution decisions.
